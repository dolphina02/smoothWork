# 시스템 아키텍처 개요

## 1. 목적

Digest(및 Inbox/Board/Reports)를 실제로 동작시키려면 화면 스펙만으로는 부족하고, 데이터를
채워 넣는 배치/파이프라인과 그걸 조회하는 API 레이어가 필요하다. 이 문서는 필요한 컴포넌트를
나열하고, 특히 **"서비스 자체가 쓰는 백엔드"와 "LLM/외부 에이전트가 쓰는 MCP 툴"을 의도적으로
분리**하는 이유와 경계를 정의한다.

각 컴포넌트의 상세 설계(API 스펙, 배치 스케줄, 에러 처리 등)는 이 문서 범위 밖이며, 필요해지는
시점에 별도 문서로 분리한다.

## 2. 컴포넌트 목록

### 2.1 Slack 요약 배치 프로세스
- 채널별로 메시지를 가져와서(Digest 3절, 새벽 5시~다음날 5시 경계 기준) LLM 요약을 호출하고
  `slack_daily_summaries`(Digest 2.3절)에 저장
- 매일 새벽 5시, 직전 하루치를 대상으로 자동 실행 (Digest 7절)

### 2.2 회의 STT+요약 파이프라인
- wav/mp3 입력 → STT 변환 → 회의 전체 내용을 LLM이 요약 → `meetings.summary_md`에 저장
  (Digest 2.1절)
- 트리거: 2.3의 업로드 화면(Digest 5.4절)에서 업로드 이벤트 발생 시 비동기로 시작
- Inbox의 발화 단위 추출(`extracted_candidates` 생성)과는 별개 산출물이다 — 이 파이프라인은
  "회의 전체 요약", Inbox 추출은 "태스크가 될 만한 발화 하나하나"를 만든다. 같은 STT 결과를
  입력으로 공유할 수는 있지만 목적과 출력이 다르므로 혼동하지 않는다

### 2.3 Frontend 서비스
- Inbox / Board / Reports / Digest 화면 전체, Digest 5.4절의 "회의 녹음 업로드" 인터페이스 포함
- 2.4(서비스 백엔드)에만 의존한다. 2.5(MCP/조회 API)는 프론트엔드가 직접 호출하지 않는다

### 2.4 서비스 백엔드 (Backend-for-Frontend)
- 프론트엔드 전용 API. Outlook 일정 동기화, LLM 프롬프트/모델 설정(로컬 LLM ↔ 외부 LLM 전환),
  캘린더-녹음 매칭 로직(Digest 2.2절) 등을 담당
- 화면 요구사항 변화에 맞춰 자유롭게 필드를 추가/변경해도 되는, Frontend와 강하게 결합된 레이어

### 2.5 조회 API / MCP Tool 서비스
- 저장된 회의 요약, Slack 채널 요약 등을 외부 LLM/에이전트가 조회할 수 있도록 노출
- 2.4(BFF)와 코드/배포 단위를 분리한다 — 같은 DB를 읽더라도 서로의 타입이나 API를 참조하지
  않는다 (자세한 이유는 4절)

## 3. 의존관계

```
[Slack API]   --> 2.1 배치 -----------------\
[오디오 파일]  --> 2.2 STT+요약 파이프라인 ----+--> DB
[Outlook API] --> 2.4 서비스 백엔드 ---------/
                     ^
                     | (내부 API 호출, 강결합)
                  2.3 Frontend

DB <-- 2.5 MCP/조회 API <-- 외부 LLM/에이전트
```

- 2.3은 2.4만 호출한다
- 2.5는 DB를 직접 읽고, 2.3/2.4와 코드 의존성이 없다
- 2.1/2.2는 DB에 직접 쓰며, 2.4/2.5와 무관하게 독립적으로 실행된다 (2.4는 2.2의 처리 상태를
  `stt_status` 폴링으로만 관찰한다 — Digest 5.4절)

## 4. 왜 2.5(MCP)를 2.4(BFF)와 분리하는가

- LLM이 쓰는 툴(2.5)의 인터페이스는 안정적이어야 다른 에이전트/워크플로가 이걸 신뢰하고 쓸 수
  있다. 화면이 바뀔 때마다(2.4가) 같이 흔들리면 외부 소비자 입장에서 곤란하다
- 반대로 화면 개발 속도를 위해 BFF는 화면 요구사항에 맞춰 응답 필드를 자유롭게 추가/변경해야
  하는데, 이게 MCP 툴 스펙에 영향을 주면 외부 소비자가 깨진다
- 두 레이어가 같은 DB 스키마를 읽더라도, API 계약(response shape, 버전 관리)은 서로 독립적으로
  진화해야 한다는 것이 이 분리의 핵심 근거
