# Task 화면 기능명세

## 1. 목적

Task 사이드바 항목은 Board(board-spec.md)를 그대로 사용하되, 보드(프로젝트)가 여러 개일 수
있다는 점을 반영해 위에 보드 스위처를 얹는다. Board 자체의 타임라인/의존관계/임팩트 분석
로직은 이 문서에서 다시 설명하지 않고 board-spec.md를 그대로 따른다 — 이 문서는 "여러 보드를
어떻게 오가는가"만 다룬다.

## 2. 스키마 갭

board-spec.md 2절은 프로젝트별 필터를 "v1에서는 필터 옵션에서 제외"로 미뤄뒀다(`projects` 테이블
부재). Task가 여러 개일 수 있다는 요구가 생겼으므로 이 backlog를 지금 끌어온다.

```sql
CREATE TABLE projects (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE tasks ADD COLUMN project_id UUID REFERENCES projects(id); -- nullable, 미배정 허용
```

`project_id`는 nullable이다 — Inbox/Today의 검토 큐에서 후보를 승인할 때 프로젝트를 지정하는
필드는 두지 않으므로(4절), 새로 확정되는 태스크는 기본적으로 미배정 상태로 시작한다.

## 3. 레이아웃

```
┌──────────────────────────────────────────────────────────────────┐
│ [보드: 전체 ▾]  [+ 새 보드]                                         │
├──────────────────────────────────────────────────────────────────┤
│                                                                      │
│              (board-spec.md 3절 레이아웃 그대로: 필터바 +             │
│               타임라인 + 임팩트 분석 슬라이드오버)                     │
│                                                                      │
└──────────────────────────────────────────────────────────────────┘
```

- 상단에 보드 스위처(드롭다운)만 추가하고, 그 아래는 board-spec.md의 레이아웃을 그대로 쓴다
- 스위처 옵션: **전체**(`project_id` 무관하게 모든 태스크 — 기존 Board 동작과 동일) + 존재하는
  프로젝트들
- 보드가 0개 또는 1개뿐이면 스위처를 숨긴다 (6절)

## 4. 보드 생성

- "+ 새 보드" 클릭 → 이름 입력 모달 → `projects` insert
- 새 보드는 태스크가 하나도 없는 빈 상태로 시작한다 — Board 8절의 "태스크가 하나도 없음" 안내를
  그대로 재사용
- 보드 삭제/이름 변경은 7절 backlog

## 5. 태스크의 프로젝트 배정

- Today/Yesterday의 검토 큐에서 후보를 승인할 때는 프로젝트 지정 필드를 두지 않는다 — 신규
  확정 태스크는 `project_id=null`("전체" 보드에서만 보임)로 시작한다
- 태스크 상세 패널(board-spec.md 6절)에 **"프로젝트"** 필드를 추가해, 여기서 배정/변경한다 —
  드롭다운으로 기존 프로젝트 선택 또는 "미배정"
- board-spec.md 9.1절의 수동 생성(draw-to-create)도 같은 필드로 즉시 프로젝트를 지정할 수 있다

## 6. 엣지 케이스

- 프로젝트가 하나도 없으면(모든 태스크가 `project_id=null`) 스위처를 숨기고 기존 Board와 동일한
  화면으로 동작한다
- 태스크를 다른 보드로 옮기면(`project_id` 변경) 원래 보드의 타임라인에서는 사라지고 옮긴 보드에
  나타난다 — `dependencies`는 프로젝트와 독립적인 축이므로, 보드 경계를 넘어 걸린 의존관계라도
  Board 6.2절의 임팩트 분석은 프로젝트 무관하게 전체 그래프를 그대로 순회한다
- "전체" 보드에서 임팩트 분석을 실행하면 다른 프로젝트의 태스크까지 영향 범위에 포함될 수 있다 —
  이 경우도 숨기지 않고 그대로 보여준다(Board 7절의 "리스크 있는 dependency만" 필터와 같은 원칙:
  맥락을 잃지 않는 쪽을 우선한다)

## 7. v1 범위 밖 (backlog)

- 보드 삭제/이름 변경 UI
- 보드별 권한/공유 설정
- 여러 태스크를 한 번에 다른 보드로 이동(일괄 이동)
