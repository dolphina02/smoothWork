# Board 화면 기능명세

## 1. 목적

확정된 `tasks`를 타임라인 위에 dependency 화살표와 함께 시각화하고, 특정 태스크가
밀릴 경우 영향받는 범위를 즉시 계산해서 보여준다. Jira/Notion에는 없는
"dependency 위반 시 자동 임팩트 분석"이 이 화면의 핵심 차별점 (README 1절 참고).

## 2. 스키마 갭 — 사전 결정 사항

현재 `tasks` 테이블에는 `start_date`, `project` 컬럼이 없다. Board 구현을 막지 않기
위해 다음과 같이 임시 처리하고, 정식 마이그레이션은 backlog로 남긴다.

| 필요한 것 | 임시 처리 | 정식 해법 (backlog) |
|---|---|---|
| 타임라인 바의 시작점 | `tasks.created_at`(태스크가 확정된 시점)을 시작점으로 사용 | `tasks.start_date` 컬럼 추가, Extraction 단계에서 추정 |
| 프로젝트별 필터 | v1에서는 필터 옵션에서 제외, "담당자별" / "전체"만 제공 | `tasks.project_tag` 또는 `projects` 테이블 추가 |
| 마일스톤 표시 | `due_date`가 있고, 선행 의존관계가 1개 이상 있으며(=어떤 체인의 결과물), 자신을 선행조건으로 하는 다운스트림 의존관계는 없는(=체인의 끝) 태스크를 "마일스톤 후보"로 표시 | `tasks.is_milestone` boolean 컬럼 추가 |
| `due_date` 없는 태스크 | 타임라인 우측 "미정" 컬럼에 별도 고정 표시 | 없음 (의도된 상태) |
| 태스크 계층(레벨)별 그룹 | v1에서는 그룹 옵션에서 제외, "담당자별" / "전체"만 제공 | `tasks.parent_task_id` 자기참조 FK 추가 (11절 참고) |

## 3. 레이아웃

```
┌──────────────────────────────────────────────────────────────────┐
│ 필터바: [담당자 ▾] [리스크만 ⬜] [그룹: 담당자별/전체] [기간: 4주 ▾]  │
├──────────────────────────────────────────────────────────────────┤
│           8/10   8/11   8/12   8/13   8/14   8/15   8/16   미정   │
│ 김도현 ──┬──────────────────────────────────────────────┬────────│
│          │  ▬▬▬▬▬▬ API 게이트웨이 인증           ◆      │        │
│ 이은지 ──┼──────────────────────────────────────────────┼────────│
│          │        ▬▬▬▬ 리포트 자동 배포                 │  [ ]   │
│ 박서연 ──┴──────────────────────────────────────────────┴────────│
│                                                                      │
│  (선택 시 우측 슬라이드오버: 임팩트 분석 패널)                       │
└──────────────────────────────────────────────────────────────────┘
```

- 상단: 날짜 축 (주 단위 눈금, 기본 4주 범위 — 좌우 스크롤/드래그로 이동)
- 좌측: 그룹 헤더 (담당자별 그룹핑이 기본값)
- 본문: 태스크 바 (`created_at` → `due_date` 구간) + 의존관계 화살표 (SVG 커넥터)
- 우측 끝 "미정" 컬럼: `due_date`가 없는 태스크를 타임라인 밖에 고정 리스트로 표시
- 태스크 바 클릭 → 우측에서 임팩트 분석 패널이 슬라이드인 (레이아웃을 밀지 않고 오버레이)

## 4. 태스크 바

- 라벨: 태스크 제목 (바 안에 fit, 넘치면 truncate + hover 툴팁 전체 표시)
- 색상: 담당자별 카테고리 컬러 (일관된 팔레트, 6~8명 기준 회전)
- 마일스톤 후보 (3절 휴리스틱): 바 끝에 ◆ 마커 추가
- `due_date` 지난 미완료 태스크: 바 테두리를 위험색(빨강)으로 강조 + 좌상단에 "지연" 뱃지

## 5. 의존관계 화살표

- `dependencies` 테이블의 `blocks`/`blocked_by`를 화살표(from → to)로 렌더링
- 화살표 색상:
  - **정상 (회색)**: 선행 태스크의 `due_date` ≤ 후행 태스크의 `due_date`(또는 선행 태스크가 이미 완료)
  - **위험 (빨강, 굵게)**: 선행 태스크의 `due_date` > 후행 태스크의 `due_date`, 즉 이미 일정 모순이
    발생한 상태 — "선행이 늦게 끝나는데 후행이 더 일찍 끝나야 함"
  - **불명확 (점선, 회색)**: 둘 중 하나라도 `due_date`가 없어 판단 불가
- 필터 "리스크 있는 dependency만" 체크 시, 정상 화살표로만 연결된 태스크/화살표는 dim 처리(투명도↓)
  하고 위험/불명확 관계만 선명하게 남긴다 (완전히 숨기지 않음 — 맥락 유지를 위해)

## 6. 태스크 상세 패널

태스크 바(또는 미정 컬럼 카드) 클릭 시 우측에서 슬라이드인. 상단에 탭 2개:
**임팩트 분석** / **관련 발언 (N)**. 기본 탭은 "임팩트 분석".

### 6.1 입력
- "N일 밀리면?" — 프리셋 버튼(3일/7일/14일) + 직접 입력 숫자 필드
- 기본값 3일

### 6.2 계산 로직
- 선택 태스크를 시작점으로 `blocks` 방향 의존관계 그래프를 BFS/DFS로 순회하여
  직접/간접 영향을 받는 모든 다운스트림 태스크 집합을 구한다
- 각 다운스트림 태스크의 `due_date`가 입력한 N일만큼 함께 밀린다고 가정하고 재계산
- 사이클이 있는 경우(순환 의존) 방문 태스크 집합으로 중복 순회를 막고, 상단에
  "순환 의존관계 감지됨" 경고를 별도로 표시 (v1: 경고만, 자동 해결 안 함)

### 6.3 출력
- **영향받는 태스크 수**: "이 변경으로 4개 태스크, 3명의 담당자에게 영향"
- **영향받는 태스크 리스트**: 태스크명, 담당자, 기존 기한 → 새 예상 기한 (취소선 → 강조)
  간접 영향은 "N단계 건너 영향"으로 구분 표시 (직접 vs 간접)
- **영향받는 마일스톤**: 3절 휴리스틱으로 판별된 마일스톤 후보가 영향 집합에 포함되면
  패널 상단에 별도 경고 배너로 강조 ("마일스톤 '베타 출시' 영향받음")
- 패널 하단: "이 변경을 실제로 반영" 버튼 (v1에서는 비활성 placeholder —
  실제 반영은 Inbox/수동 편집 경로로만 가능, Board는 시뮬레이션 전용)

### 6.4 관련 발언 탭

이 태스크가 언급된 모든 원본 발화(Slack 메시지 / 회의 발화)를 시간순으로 나열한다.
"이 태스크가 어디서 왜 나왔는지" 를 다시 찾아가는 트레이스 기능 — Jira/Notion에는
없는, 이 프로젝트의 핵심 가치(README 1절 "회의/대화 → 구조화된 태스크 자동 변환")를
Board에서도 체감하게 하는 진입점이다.

**표시 항목** (발언마다):
- 출처 뱃지 (Slack / WAV / MP3) + 채널명 또는 화자명 + 발생 시각
- 발화 원문 스니펫 (Slack이면 말풍선, 오디오면 타임스탬프 텍스트 — Inbox 상세 패널과 톤 일치)
- 구분 태그: **최초 추출** (이 태스크를 처음 만든 발화) vs **후속 언급** (이후 회의/대화에서 같은
  태스크가 다시 언급되어 매칭된 발화)
- 오디오 소스는 "▶ 오디오에서 보기" 링크로 원본 회의 재생 위치까지 이동 가능 (Inbox와 동일 패턴)
- 발언이 하나도 없는 경우는 구조적으로 없어야 정상이다 (모든 확정 태스크는 최소 1개의
  최초 추출 발화를 가짐) — 만약 비어 있다면 데이터 정합성 문제로 간주하고 경고 배너 표시

**스키마 갭**: 현재 `tasks.source_candidate_id`는 후보 1개만 가리킬 수 있어 "후속 언급"을
표현할 수 없다. `extracted_candidates`에 `matched_task_id UUID REFERENCES tasks(id)` (nullable)
컬럼을 추가해서, Structuring 단계(README 2절 (3))에서 신규 태스크 대신 기존 태스크에 매칭된
후보는 이 컬럼을 채우도록 한다. 관련 발언 탭은 `source_candidate_id`로 연결된 항목을
"최초 추출"로, `matched_task_id`로 연결된 항목들을 "후속 언급"으로 시간순 정렬해 보여준다.

## 7. 필터

- **담당자별**: 다중 선택, 선택된 담당자의 태스크와 그들이 연결된 의존관계만 표시
- **리스크 있는 dependency만**: 5절 참고
- **그룹 기준**: 담당자별(기본) / 전체(그룹 헤더 없이 평평하게) / 태스크 계층별 (11절 참고, 스키마 갭으로 v1 제외)
- **기간**: 2주 / 4주(기본) / 8주 — 타임라인 좌우 스크롤은 항상 가능, 이 옵션은 초기 줌 레벨만 결정

## 8. 엣지 케이스

- 태스크가 하나도 없음 → "아직 확정된 태스크가 없습니다. Inbox에서 후보를 승인해보세요" 안내 + Inbox 바로가기
- 순환 의존관계 → 6.2 참고, 화면에는 경고 아이콘만 노출하고 Board 렌더링 자체는 정상 진행
- 담당자 미배정 태스크 → "담당자 미정" 그룹으로 별도 표시 (그룹핑이 "담당자별"일 때)
- 매우 긴 의존 체인(예: 10단계 이상) → 임팩트 패널 리스트를 "직접 영향(N개)"와 "간접 영향(N개, 펼쳐보기)"로 접어서 표시, 기본은 접힌 상태

## 9. 와이어프레임 범위 vs 실제 구현 범위

`wireframes/board.html`은 정적 목데이터 기반 프로토타입이라 아래 인터랙션은 구현하지
않았다. 하지만 **실제 개발 단계(Phase 4)에서는 필수 기능**으로 넣는다 — Jira/Notion
대비 "직접 그리고 옮길 수 있는 타임라인"이 이 화면의 실사용성을 좌우하기 때문.

### 9.1 타임라인에 직접 일정 추가 (draw-to-create)
- 담당자 행의 빈 영역을 클릭+드래그하면 새 태스크 바를 그릴 수 있다
- 그린 구간이 `tasks.start_date`(2절에서 언급한 스키마 확장) ~ `due_date`가 됨
- 드래그를 놓는 즉시 바 안에서 제목 인라인 입력 → 확정 시 `tasks`에 바로 insert
  (`source_candidate_id`는 null. Inbox 파이프라인을 거치지 않은 수동 생성임을 구분하기 위해
  `tasks.source` 같은 컬럼 추가 필요 — 추가 스키마 갭)
- 수동 생성이므로 `human_review_log`에는 기록하지 않는다 (추출/검토 행위가 아니므로)

### 9.2 기존 태스크 바 드래그 앤 드롭으로 재일정
- 바 몸통을 좌우로 드래그 → `start_date`/`due_date`를 함께 이동
- 바 가장자리를 드래그 → 시작 또는 종료 중 하나만 리사이즈
- 드래그 중인 태스크에 다운스트림 의존관계가 있으면, 놓는 순간 6.2절의 임팩트 분석 로직을
  그대로 재사용해 "N개 태스크가 함께 밀립니다 — 같이 반영할까요?" 확인 모달을 띄운다
  - **함께 반영**: 다운스트림 태스크들의 `due_date`도 동일 폭으로 shift, 각 태스크마다
    `human_review_log`에 `action=date_changed`로 기록 (`reasoning`: "상위 태스크 일정 변경으로
    인한 연쇄 조정")
  - **이 태스크만 반영**: 드래그한 태스크만 반영하고, 그로 인해 새로 발생한 리스크 있는
    dependency 화살표(5절)가 화면에 경고로 남는다
- 이 인터랙션이 들어가면 6.3절의 "적용" 버튼(현재 비활성 placeholder)은 별도 버튼이 아니라
  드래그 동작 자체로 대체된다 — 임팩트 패널은 "드래그하기 전에 미리 시뮬레이션해보는" 용도로 남는다

## 10. 계획 vs 실제 일정 오버레이

계획한 일정과 실제로 진행된 일정은 어긋나기 마련이다. Board에서 둘을 겹쳐 보면서
"어디서 얼마나 밀렸는지"를 한눈에 파악할 수 있어야 한다. **와이어프레임에는 구현하지
않고 스펙만 남긴다** (9절과 마찬가지로 Phase 4 실제 구현 대상).

### 10.1 스키마 갭
현재 `tasks`에는 계획/실제를 구분할 필드가 없다. 다음이 필요하다:

| 필드 | 용도 | 채워지는 시점 |
|---|---|---|
| `baseline_start_date`, `baseline_due_date` | 최초 계획 스냅샷 (불변) | 태스크가 처음 확정될 때(Inbox 승인 or 9.1 수동 생성) 1회만 기록, 이후 절대 갱신하지 않음 |
| `start_date`, `due_date` | 현재 유효한 계획 (가변) | 9.2 드래그, Inbox 수정 등으로 계속 갱신됨 — "지금 기준 계획" |
| `actual_start_date` | 실제 착수 시점 | `status`가 `open → in_progress`로 바뀌는 시점 자동 기록 |
| `completed_at` | 실제 완료 시점 | `status`가 `→ done`으로 바뀌는 시점 자동 기록 |

`tasks.status`도 현재는 `open` 기본값만 정의되어 있어(README 3절), `in_progress`/`done`을
포함하도록 CHECK 제약을 확장해야 위 자동 기록이 가능하다.

### 10.2 타임라인 시각화
- 표시 모드 토글을 필터바에 추가: **실제만**(기본, 지금 wireframe과 동일) / **계획만** / **오버레이**
- 오버레이 모드에서 태스크 행마다 바 2개를 겹쳐 그린다:
  - **계획 바**: 옅은 채도 + 점선 테두리의 "고스트" 바, `baseline_start_date` ~ `baseline_due_date`
  - **실제 바**: 기존과 동일한 실선 바, `actual_start_date`(없으면 `start_date`) ~
    `completed_at`(진행 중이면 오늘까지 연장해서 그리고 우측 끝에 진행중 표시 빗금 패턴 적용)
  - 두 바의 끝점이 다르면 그 간격을 짧은 커넥터 선 + "+N일" / "-N일" 라벨로 표시
    (+는 지연, -는 조기 완료 — 색상은 지연=빨강, 조기=초록, 동일=표시 안 함)
- 계획 바가 없는 태스크(9.1로 수동 생성 후 baseline을 아직 못 만든 경우 등)는 실제 바만 단독으로 그리고
  "계획 없음" 표시를 hover 툴팁에 남긴다

### 10.3 태스크 상세 패널 — "계획 대비 실제" 탭
6/6.4절에서 만든 탭 구조(임팩트 분석 / 관련 발언)에 세 번째 탭 **계획 대비 실제**를 추가한다.
- 계획 시작/종료 vs 실제(또는 현재 예상) 시작/종료를 나란히 표시
- 변동 폭을 일수로 요약 ("계획보다 4일 지연")
- 관련 발언 탭(6.4)과 연결: 지연 사유를 짐작할 수 있는 시점 근처의 발언이 있으면
  "이 시점 전후 발언" 형태로 교차 참조 링크 제공 (구체 로직은 별도 설계 필요, v1 스펙 범위 밖)

### 10.4 엣지 케이스
- 진행 중(미완료) 태스크의 "실제 종료일"은 존재하지 않으므로, 오늘 날짜까지 임시로 그리고
  실제 완료 전까지는 변동값을 "잠정 지연"으로 표시 (완료 전까지는 확정치 아님을 시각적으로 구분)
- 계획보다 실제가 더 이른 경우(조기 완료)도 동일한 메커니즘으로 표시 (음수 변동)
- baseline이 아예 없는 태스크(마이그레이션 이전 데이터 등)는 오버레이 모드에서 자동으로
  "계획만" 표시를 생략하고 실제 바만 렌더링

## 11. 태스크 계층(레벨)별 보기

담당자별/전체 그룹만으로는 "이 큰 작업 밑에 어떤 하위 작업들이 있는지"를 볼 수 없다.
Epic/Task/Subtask 같은 계층 구조로도 Board를 볼 수 있어야 한다. **와이어프레임에는
구현하지 않고 스펙만 남긴다** (9·10절과 동일하게 Phase 4 실제 구현 대상).

### 11.1 데이터 모델
- `tasks.parent_task_id UUID REFERENCES tasks(id)` (nullable, 자기참조) 추가
- 이 관계는 `dependencies`(선후행 순서 관계)와 **완전히 다른 축**이다 — 하위 태스크라고
  선행 관계가 있는 건 아니고, 같은 부모 아래 형제 태스크끼리 dependency로 얽힐 수도 있다.
  두 관계는 서로 독립적으로 유지한다.
- level(깊이)은 저장하지 않고 `parent_task_id` 체인을 따라 조회 시점에 계산한다
  (개인용 도구 규모에서는 태스크 수가 적어 성능 문제 없음 — 데이터가 커지면 비정규화 컬럼
  추가를 재검토)
- UI 상 들여쓰기는 최대 3단계(Level 0~2)까지만 지원 권장. 그 이상 깊어지면 Inbox 검토
  단계에서 "분해가 과도함" 경고를 주는 것도 backlog로 고려
- 순환 참조 방지(자기 자신 또는 자신의 자손을 parent로 지정하지 못하도록)는 DB 제약만으로
  불가능해 애플리케이션 레벨 검증이 필요 — Inbox/수동 편집 저장 시점에 체크
- Extraction 단계(README 2절 (2))에서 LLM이 "이 발화가 기존 태스크의 하위 작업을
  가리키는지"까지 판단해야 하는데, 이는 Phase 3 프롬프트 설계 범위이며 이 스펙에서는
  다루지 않는다 — 우선은 Inbox/Board에서 수동으로 부모를 지정하는 경로만 있으면 된다

### 11.2 사이드바 (계층별 그룹 모드)
- 담당자 라벨 목록 대신 들여쓰기된 트리 목록으로 전환
- 각 노드: 들여쓰기(레벨 × 16px) + 접기/펼치기 화살표(자식이 있는 경우) + 담당자 색점 + 제목
- 접힌 상태에서는 자식 태스크들이 사이드바/타임라인 모두에서 숨겨진다

### 11.3 타임라인 (계층별 그룹 모드)
- 리프 태스크(자식 없음): 기존과 동일한 방식으로 바를 그린다
- 자식이 있는 상위 태스크: 편집 불가능한 **롤업 바**를 그린다 — 구간은 모든 하위 태스크의
  `min(start)` ~ `max(due)`로 자동 계산, 담당자색 대신 중립색(옅은 회색)에 빗금 패턴으로
  구분해 "이건 계산된 요약이지 실제 일정이 아님"을 시각적으로 알린다
- 하위 태스크를 펼치면 롤업 바 아래로 각 하위 태스크 바가 인덴트되어 나타난다
- dependency 화살표(5절)는 계층과 무관하게 실제 태스크(리프든 상위든) 사이에 그대로 그린다 —
  접혀서 화면에 안 보이는 하위 태스크가 연결된 화살표는, 보이는 조상 태스크(롤업 바)로
  경로를 재연결해서 그린다 (Jira 롤업 Epic 화살표와 동일한 관례)

### 11.4 엣지 케이스
- 상위 태스크에 하위가 하나도 없으면 그냥 리프처럼 단독 표시
- 하위 태스크의 담당자가 상위와 다른 경우가 일반적 — 롤업 바는 중립색을 쓰지만 트리에서는
  각 노드 고유의 담당자 색점을 유지해 정보 손실이 없게 한다
- 계층별 그룹 모드에서는 "담당자" 필터가 계층 트리를 가지치기하는 방식으로 동작 —
  선택된 담당자의 태스크가 하나라도 포함된 상위 경로는 남기고, 나머지는 숨긴다
