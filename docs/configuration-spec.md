# Configuration 화면 기능명세

## 1. 목적

Configuration 화면은 외부 연동 설정과 알림 설정을 한 곳에서 관리하는 진입점이다. v1 범위에서는 다음 4개 영역을 다룬다.

- LLM 모델 엔드포인트 및 인증 설정
- Outlook 연동 상태 및 재인증/연결 해제
- Slack 워크스페이스/채널 연동 및 동기화 대상 설정
- 알람/알림 정책 설정

이 화면은 단순한 설정 입력 폼이 아니라, 서비스가 실제로 데이터를 수집·요약·알림할 때 필요한 연결 상태와 인증 상태를 확인하고, 문제 발생 시 재인증 또는 재구성을 유도하는 운영 화면으로 동작한다.

## 2. 화면 구조

### 2.1 전체 레이아웃

- 좌측 사이드바에서 Configuration 선택
- 중앙 메인 영역은 카드형 섹션이 세로로 나열됨
- 각 카드 섹션은 독립적으로 저장/연결/재인증 상태를 가진다
- 우측 고정 LLM 채팅 패널은 유지되며, 설정 화면에서도 동일하게 보인다
- 설정 값은 즉시 저장 원칙을 따르되, 위험한 값(토큰/키/시크릿)은 저장 직후 마스킹 표시를 유지한다

├──────────────────────────────────────────────────────────────────────┤

│ 상태: 연결됨 · dora@company.com · 마지막 동기화 3분 전                │

│ Slack 연결                                                          │

│ [저장]                                                              │

## 3. 사용자 시나리오

### 3.1 LLM 설정 초기화
- 사용자가 첫 실행 시점에 LLM provider를 설정하지 않은 상태로 진입하면 화면 상단에 "LLM이 설정되지 않았습니다" 경고를 노출한다.
- 사용자는 Local 또는 External 중 하나를 선택하고 endpoint/model name을 입력한다.
- 저장이 완료되면 요약 생성 및 채널 분석이 다음 배치부터 정상 동작한다.

### 3.2 Outlook 재인증
- 사용자가 Outlook 동기화가 중단되었음을 확인한다.
- 설정 화면에서 "재인증"을 선택하면 Microsoft OAuth 플로우가 실행된다.
- 인증에 성공하면 마지막 동기화 시각과 연결 계정 정보를 갱신한다.
- 토큰 만료 상황은 사용자에게 경고 메시지로 표시되며, 데이터는 유지된다.

### 3.3 Slack 채널 관리
- 사용자는 워크스페이스를 연결하고 "+ 채널 추가"로 전송된 목록에서 원하는 채널을 선택한다.
- 이미 추적 중인 채널은 중복 선택되지 않는다.
- 선택한 채널은 기본적으로 활성 상태로 저장되며, 이후 비활성화/재활성화가 가능하다.

### 3.4 알람 설정
- 사용자는 중요한 이벤트별 알람을 켜거나 끄고, 알람 전송 대상과 일일 브리핑 시간을 조정한다.
- 저장 후 테스트 전송 버튼을 통해 알람이 실제로 발송되는지 확인할 수 있다.

## 4. 기능 요구사항

### 4.1 공통 요구사항
- FR-01: 각 섹션은 독립적으로 상태를 표시하고 저장할 수 있어야 한다.
- FR-02: 유저는 설정 변경 후 저장 결과를 즉시 확인할 수 있어야 한다.
- FR-03: 민감 정보는 평문 노출 없이 마스킹 처리되어야 한다.
- FR-04: 연결 실패/권한 만료 시 경고 배너와 재시도 또는 재인증 CTA를 제공해야 한다.

### 4.2 LLM 요구사항
- FR-05: 사용자는 Provider를 `local` 또는 `external`로 전환할 수 있어야 한다.
- FR-06: `endpoint`와 `model_name`은 필수이며, external provider는 API key를 입력해야 한다.
- FR-07: 값 저장 시 서버는 `PUT /settings/llm`을 호출하고, 저장 결과를 화면에 반영한다.
- FR-08: 설정이 비어 있거나 잘못된 경우, 해당 상태를 화면에 분명히 표시해야 한다.

### 4.3 Outlook 요구사항
- FR-09: Outlook 연결 상태, 마지막 동기화 시각, 재인증 필요 여부를 표시해야 한다.
- FR-10: 연결 해제 시 refresh token을 폐기하고, 기존 meetings 데이터는 보존해야 한다.
- FR-11: 동기화 실패 시 화면은 전체 기능을 정지시키지 않고 경고 메시지로 안내해야 한다.

### 4.4 Slack 요구사항
- FR-12: 워크스페이스 연결 상태와 채널 목록 상태를 함께 보여줘야 한다.
- FR-13: 채널 추가 시 중복 추가를 막고, 활성/비활성 상태를 관리할 수 있어야 한다.
- FR-14: 비활성 채널은 다음 배치에서 제외되지만 기존 요약 내역은 유지해야 한다.

### 4.5 알람 요구사항
- FR-15: 일일 브리프 시간과 이벤트별 알람 설정을 변경할 수 있어야 한다.
- FR-16: 알람 대상(Email/Slack/Webhook/Desktop)은 선택적으로 활성화/비활성화할 수 있어야 한다.
- FR-17: 테스트 전송이 실패하더라도 전체 설정은 유지되어야 한다.

## 5. 비기능 요구사항

### 5.1 보안
- 비밀번호, API key, OAuth secret, 토큰은 화면에 평문으로 노출하지 않는다.
- 저장된 secret은 서버의 secure storage에 보관하고 UI는 참조 값 또는 마스킹된 값을 보여준다.

### 5.2 신뢰성
- 동기화/배치 실패는 특정 섹션에만 영향을 주고 전체 화면을 막지 않는다.
- 연결 상태가 붕괴된 경우 사용자는 즉시 재인증 또는 재시도 액션을 수행할 수 있어야 한다.

### 5.3 UX
- 각 카드 섹션은 독립적으로 읽고 수정할 수 있어야 하며, 한 섹션 오류가 다른 섹션에 영향을 주지 않아야 한다.
- 경고 상태는 색상, 배너, 액션 문구를 통해 이해 가능해야 한다.

## 6. 수용 기준 (Acceptance Criteria)

### 6.1 LLM 설정
- Provider를 Local로 선택하면 API key 입력이 비활성화되고 endpoint 입력이 유지된다.
- External 선택 시 API key 입력이 노출되고 저장이 실패하면 필드 오류를 보여준다.
- 저장 성공 후 설정 상태가 표시된다.

### 6.2 Outlook
- 연결된 상태에서 마지막 동기화 시각과 계정 이메일이 노출된다.
- 토큰 만료 시 "재인증 필요" 배너와 재인증 버튼이 표시된다.
- 연결 해제 수행 후에도 기존 미팅 데이터는 보존된다.

### 6.3 Slack
- 이미 추가된 채널은 중복 선택되지 않는다.
- 비활성화된 채널은 다음 배치 대상에서 제외되고, 기존 데이터는 유지된다.

### 6.4 알람
- 사용자가 알람을 활성화/비활성화하면 저장 후 상태가 반영된다.
- 테스트 전송 실패 시 사용자에게 실패 메시지를 표시하고 기존 설정을 유지한다.

## 7. 공통 UX 규칙

### 3.1 입력 동작

- 모든 설정 입력은 섹션별로 독립적으로 저장한다
- 사용자 입력 후 즉시 저장은 기본값으로 처리하되, 민감한 값은 저장 확인 메시지를 잠깐 보여준다
- 저장 실패 시 해당 필드 아래에 에러 메시지를 표기하고, 재시도 가능 상태를 유지한다
- 연결 상태가 비정상일 경우, 해당 카드 상단에 경고 배너를 노출한다

### 3.2 상태 표현

- `connected`: 정상 연결
- `disconnected`: 연결 없음
- `requires_reauth`: 토큰 만료 또는 권한 회수
- `syncing`: 동기화 중
- `error`: 마지막 동기화/요청 실패

상태 텍스트는 색상으로 표시되며, 상태 문자열은 반드시 설명 가능한 문구를 사용한다.

### 3.3 보안 규칙

- API 키, OAuth client secret, refresh token, Slack token은 화면에서 평문으로 보이지 않는다
- 저장 후에는 마스킹된 값으로 렌더링한다
- 새 값 입력 시 "기존 값 유지" 또는 "새 값 저장" 상태를 명확히 구분한다
- 실제 secret은 서버의 secure storage에 보관하고, 화면은 `api_key_ref` 또는 `token_ref` 형태만 다룬다

## 4. LLM 모델 설정

### 4.1 목적

LLM 모델 선택과 엔드포인트 구성을 통해 전체 요약/분류 파이프라인이 어떤 모델을 쓸지 결정한다. `backend-api-spec.md`의 `llm_settings`와 동일한 원칙을 사용한다.

### 4.2 필드 정의

| 필드 | 타입 | 필수 | 설명 |
|---|---|---:|---|
| `provider` | enum | O | `local` 또는 `external` |
| `endpoint` | string | O | Local 서버 URL 또는 외부 API base URL |
| `model_name` | string | O | 모델 이름 예: `gpt-4o-mini`, `llama3.1:8b` |
| `api_key_ref` | string | External만 | 실제 값 저장 금지, 참조값만 유지 |
| `timeout_seconds` | int | O | 기본 30초 |
| `temperature` | number | 선택 | 요약 품질/랜덤성 제어 |
| `updated_at` | datetime | O | 마지막 설정 변경 시각 |

### 4.3 UX 동작

- Provider 토글: Local / External
- Local 선택 시 endpoint는 로컬 서버 URL을 입력하고 API key 필드는 비활성화된다
- External 선택 시 endpoint, model name, API key 입력이 노출된다
- 저장 버튼 클릭 시 서버에 `PUT /settings/llm` 요청을 보낸다
- 저장 후 UI는 성공 메시지를 표시하고, 설정 상태를 `ready` 또는 `needs_attention`으로 갱신한다
- 저장 전 입력 값 검증은 다음 규칙을 따른다:
  - endpoint는 http/https URL 형식이어야 함
  - model_name은 비어 있으면 안 됨
  - external provider에서 API key는 반드시 입력되어야 함

### 4.4 에러 상태

- endpoint 연결 실패: "모델 서버에 연결할 수 없습니다" 안내
- API key 만료/권한 문제: "재인증 또는 키 갱신이 필요합니다" 안내
- 약한/잘못된 설정은 저장을 허용하지 않고 필드별 오류를 표시한다

## 5. Outlook 연동

### 5.1 목적

Outlook 캘린더와 회의 데이터를 동기화해, 회의 일정, 녹음, 요약, follow-up task 생성을 연결한다. `backend-api-spec.md`의 동기화 규칙을 그대로 사용한다.

### 5.2 필드와 상태

| 항목 | 설명 |
|---|---|
| `account_email` | 연결된 계정 이메일 |
| `sync_status` | connected / disconnected / requires_reauth / syncing / error |
| `last_sync_at` | 마지막 성공 동기화 시각 |
| `sync_window_days` | 조회 범위, 기본 과거 7일 ~ 미래 30일 |
| `polling_interval_minutes` | 기본 5분 |
| `oauth_scope` | `Calendars.Read`, `offline_access` 등 |

### 5.3 UX 동작

- 미연결 상태: "연결" 버튼 노출
- 연결된 상태: 사용자 이메일, 마지막 동기화 시각, 동기화 상태 뱃지 노출
- 권한 만료 상태: "재인증 필요" 경고 배너와 재인증 버튼 노출
- 연결 해제 버튼은 refresh token을 폐기하고 이후 동기화를 중단한다
- 이미 저장된 meeting/recording 데이터는 보존되며, 연결 해제 후에도 삭제하지 않는다

### 5.4 API/데이터 연동

- `GET /sync/status`로 연결 상태, 마지막 동기화 시각, `requires_reauth` 값을 조회한다
- 동기화 범위와 주기는 설정 카드에서 확인 가능하되, v1 에서는 변경 UI보다 상태 확인 위주로 운영한다
- 실제 재인증 플로우는 별도 OAuth 모달/페이지로 진입한다

### 5.5 에러 처리

- 동기화 실패 시 카드 상단에 경고 배너를 보여주고 마지막 성공 시각만 유지한다
- 토큰 만료 시 `requires_reauth=true`를 표시하고, 배경 동기화를 중단하지 않는다
- 사용자에게는 “다시 연결”만 요구하고, 데이터 삭제는 하지 않는다

## 6. Slack 연결 및 채널 관리

### 6.1 목적

Slack 워크스페이스의 인증 상태와 요약 대상 채널 목록을 관리한다. `slack-summary-batch-spec.md`의 `tracked_slack_channels` 정책과 맞물린다.

### 6.2 필드 정의

| 항목 | 설명 |
|---|---|
| `workspace_name` | Slack workspace 이름 |
| `workspace_id` | 워크스페이스 고유 ID |
| `oauth_status` | connected / disconnected / requires_reauth |
| `tracked_channels` | 요약 대상 채널 목록 |
| `token_ref` | 안전하게 저장된 토큰 참조값 |

### 6.3 UX 동작

- 연결되지 않은 상태: "Slack 연결" 버튼으로 OAuth 시작
- 연결된 상태: workspace 이름, 연결 시각, 채널 수 표시
- "+ 채널 추가" 버튼으로 채널 검색/선택 UI를 연다
- 각 채널 행은 다음 정보를 표시한다:
  - 채널 이름
  - 활성/비활성 상태
  - 마지막 요약 시각
  - [비활성화] / [활성화] / [제거] 액션
- 중복 채널은 추가 불가
- 비활성화된 채널은 다음 배치에서 제외되지만 기존 요약 데이터는 유지한다

### 6.4 Workplace/Channel validation

- 채널 추가 전에는 Slack API를 통해 현재 워크스페이스의 공개/비공개 채널 목록을 조회해 후보 목록을 보여준다
- 이미 등록된 채널은 검색 결과에서 제외한다
- 권한 부족 또는 토큰 만료 시 재인증 상태로 전환한다

## 7. 알람 설정

### 7.1 목적

알림 설정은 요약 생성 실패, 일정 변경, 리마인더, 일일 브리프 전달 등을 제어한다. 알림 대상은 Email, Slack, Webhook, Desktop Push를 지원한다.

### 7.2 필드 정의

| 필드 | 타입 | 설명 |
|---|---|---|
| `daily_brief_time` | time | 매일 요약 브리프 생성 시간 |
| `notify_on_summary_failure` | boolean | 요약 실패 시 알림 |
| `notify_on_meeting_change` | boolean | 일정 변경/취소 알림 |
| `notify_on_follow_up_due` | boolean | follow-up 마감 알림 |
| `severity_threshold` | int | 중요도 임계치 |
| `destinations` | array | `email`, `slack`, `webhook`, `push` |
| `webhook_url_ref` | string | webhook endpoint 참조값, 실제 URL은 저장 시 마스킹 |

### 7.3 UX 동작

- 알람 유형은 토글형으로 선택한다
- 전역 알람 ON/OFF, 각 알림 이벤트별 ON/OFF를 따로 관리한다
- 요약 실패 알림은 기본값으로 ON
- 일일 브리핑 시간은 로컬 시간으로 설정
- 이벤트별 리마인더는 중요도 기준으로 필터링되며, threshold 값보다 낮은 항목은 무시한다

### 7.4 알림 테스트

- v1은 “테스트 전송” 버튼을 허용하되, 실제 전송 실패 시 메시지만 표시한다
- 테스트 전송은 서버가 별도 비동기 요청으로 보낸 뒤 응답 결과를 UI에 반영한다
- 테스트 전송은 전체 설정 저장과 별개로 동작할 수 있다

## 8. 저장/검증 흐름

### 8.1 저장 순서

1. 사용자가 설정을 수정한다
2. 필드 수준 검증을 수행한다
3. 유효하지 않으면 오류 메시지를 표시하고 저장을 중단한다
4. 유효하면 각 섹션별 API로 전송한다
5. 서버는 성공/실패 상태를 응답한다
6. 화면은 해당 섹션의 상태 뱃지와 경고 배너를 갱신한다

### 8.2 재시도 정책

- 저장 실패는 화면에 에러 상태 유지
- 연결/인증 실패는 재시도 버튼을 노출
- 네트워크 오류 시 사용자에게 “잠시 후 다시 시도해 주세요” 메시지 표시
- 인증 관련 오류는 재인증 플로우로 연결한다

## 9. 엣지 케이스

- LLM 설정이 비어 있거나 잘못된 경우: 요약 생성 시 배치/파이프라인이 실패하고, 화면 상단에 "LLM이 설정되지 않았습니다" 경고를 표시한다
- Outlook 연동이 끊긴 상태에서 Yesterday/Meeting 화면에 진입하면 각각 "Outlook과 연동되지 않았습니다" 안내와 설정 화면 바로가기 링크를 보인다
- Slack 토큰이 만료되면 채널 목록이 잠시 비활성화되고 재인증 버튼이 노출된다
- 알람 설정이 비어 있더라도 핵심 요약/캘린더 기능은 정상 동작해야 한다

## 11. API 연동 요약

| 영역 | 사용 API | 비고 |
|---|---|---|
| LLM 설정 | `GET /settings/llm`, `PUT /settings/llm` | secret은 노출하지 않음 |
| Outlook | `GET /sync/status` | 연결 상태와 마지막 동기화 시각 |
| Slack | Slack OAuth + 채널 목록 API | 설정 화면에서 관리 |
| Alarm | 내부 설정 저장 API | 저장/테스트 전송 지원 |

이 화면은 각 외부 연동이 “정상 동작 여부”를 한눈에 보여주는 운영센터 역할을 수행해야 한다. 사용자는 특정 연결이 실패했는지를 보면서 바로 재인증, 채널 관리, 알림 조건 조정까지 이어갈 수 있어야 한다.
