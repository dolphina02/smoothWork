# 조회 API / MCP Tool 서비스 명세

## 1. 목적

저장된 데이터(미팅 요약, Slack 채널 요약, 태스크, 리포트 등)를 외부 LLM/에이전트가 조회할 수
있도록 MCP 툴로 노출한다. architecture.md 4절의 원칙대로 BFF(backend-api-spec.md)와 별개
프로세스/코드베이스로 유지하며, DB를 직접 읽는다 — BFF의 응답 형태나 내부 구현이 바뀌어도 이
레이어는 영향받지 않는다.

## 2. 설계 원칙

- **읽기 전용 (v1)**: 외부 에이전트가 데이터를 변경할 수 없다. 쓰기는 오직 Inbox/Board 등
  사람이 검토하는 화면을 통해서만 일어난다 — `human_review_log`로 모든 변경을 추적하는 기존
  원칙(inbox-spec.md 6절)을 MCP 경유로 우회할 수 있는 길을 만들지 않는다
- **안정적인 응답 스키마**: BFF는 화면 요구사항에 맞춰 자유롭게 바뀌어도 되지만, 이 레이어의
  응답이 바뀌면 외부 소비자(에이전트)가 깨진다. 필드 추가는 허용하되 기존 필드 제거/의미 변경은
  버저닝이 필요하다는 원칙만 v1에서 문서로 남기고, 실제 버전 관리 체계는 필요해지면 만든다
- DB 스키마를 그대로 노출하지 않는다. 툴별로 목적에 맞게 가공된 응답을 반환한다 (예: 여러
  테이블을 JOIN한 raw 결과가 아니라 "그 날의 다이제스트"처럼 이미 정리된 형태)

## 3. 툴 목록 (초안)

| 툴 | 입력 | 출력 | 비고 |
|---|---|---|---|
| `get_daily_digest` | `date` (YYYY-MM-DD) | 그 날짜의 미팅 목록(제목, 시간, 요약 유무, 요약 본문) + Slack 채널 요약 목록 | Digest 화면(digest-spec.md 4절)과 1:1 대응. 처리 중/실패 항목은 상태만, 본문은 생략 |
| `get_meeting_summary` | `meeting_id` 또는 `title_keyword` + 날짜 범위 | 요약(`summary_md`) + 옵션으로 전문(`transcript_json`) | 매칭 여러 건이면 후보 목록(제목/날짜/id)만 반환해 다시 좁혀 조회하게 함 |
| `get_slack_channel_summary` | `channel_name`, `date` 또는 날짜 범위 | 해당 기간 요약 배열 (channel, date, content_md, message_count) | — |
| `search_tasks` | 키워드/담당자/상태 필터 | 매칭되는 `tasks` (Board/Inbox와 동일 소스) | 조회 전용 — 생성/수정/승인은 이 툴로 하지 않음 (2절 원칙) |
| `get_report` | `report_id` 또는 `type`(team/executive) + 최신 N개 | reports-spec.md의 `sections` 구조 그대로 | — |

## 4. 인증/권한

- 개인용 도구이므로 v1은 단일 API 키 또는 로컬 전용(외부 네트워크에 노출하지 않음)으로 충분
- 외부 배포/다중 사용자 지원은 9절 backlog

## 5. 에러 처리

- 존재하지 않는 리소스를 조회하면 빈 결과를 반환하고, 예외로 전체 요청을 실패시키지 않는다 —
  에이전트가 "데이터 없음"과 "요청 자체의 에러"를 구분할 수 있어야 하기 때문
- 내부 DB 연결 실패 등 진짜 에러는 에러로 반환하되, 내부 스키마/쿼리 정보를 그대로 노출하지 않는다

## 6. v1 범위 밖 (backlog)

- 쓰기/변경 툴 (승인/반려/태스크 생성 등은 의도적으로 제외 — 2절 원칙)
- 응답 스키마 버전 관리 체계
- 다중 사용자 인증/권한 분리
- 페이지네이션/대용량 결과 스트리밍 (v1은 결과 개수가 적은 개인용 규모를 전제)
