# 공통 스펙: IA, 용어, UX 기본 규칙

## 1. 목적

이 문서는 화면별 기능명세가 반복해서 다루는 공통 규칙을 한곳에 모아 정리한 기준 문서다.

- 앱 전체 IA와 화면 전환 구조
- 공통 UX 패턴(리스트-상세, 즉시 저장, 채팅 패널, 선택형 액션)
- 도메인 용어와 핵심 데이터 모델
- v1 범위와 backlog 정책
- 화면별 문서의 역할 분담

화면별 스펙은 이 문서의 공통 규칙을 전제하고, 해당 화면만의 세부 로직에 집중한다. 중복되는 설명은 여기로 통합한다.

## 2. 서비스 IA와 화면 맵

### 2.1 앱 셸

- 좌측 아이콘 사이드바로 화면 전환
- 우측 고정 LLM 채팅 패널은 화면 전환과 무관하게 유지
- 기본 진입 화면은 Today
- 화면 전환은 탭 스타일의 즉시 전환, 별도 확인 모달 없음

### 2.2 화면 구성

| 사이드바 항목 | 문서 | 설명 |
|---|---|---|
| Yesterday | `digest-spec.md` | 미팅/Slack 요약과 Follow-up Task 검토 |
| Today | `today-spec.md` | 오늘 할 일 + pending triage |
| Task | `task-spec.md` | 태스크 보드/프로젝트 중심 작업 화면 |
| Meeting | `meeting-list-spec.md` | Outlook 일정 전체 브라우징 |
| Configuration | `configuration-spec.md` | Outlook/LLM/Slack 설정 |

- Reports는 이번 IA 개편 범위 밖이며 별도 논의 대상
- 옛 Inbox는 Today로 흡수
- Digest는 문서/데이터 계층상으로는 기존 이름을 유지할 수 있지만, 앱 내 라벨은 Yesterday

## 3. 공통 UX 규칙

### 3.1 리스트-상세 패턴

대부분의 화면은 좌측 리스트 + 우측 상세 패널 구조를 따른다.

- 선택된 항목이 좌측에 나열됨
- 상세 정보는 우측에서 렌더링
- 상세/편집 행위는 화면 단위가 아니라 항목 단위로 동작
- 선택 전환과 편집 전환은 즉시 반영, 별도 저장 버튼을 강요하지 않음

### 3.2 즉시 저장 원칙

- 사용자가 체크하거나 수정한 값은 필드 단위로 즉시 저장되는 것으로 간주한다
- "저장되지 않은 변경사항" 개념은 v1 범위에서 제외한다
- 그래도 편집/수정 사이에 확인이 필요한 경우는 해당 화면에서 로컬 UI로만 처리한다

### 3.3 채팅 패널 원칙

- 우측 LLM 채팅은 읽기 전용으로 운영한다
- 채팅으로 태스크를 승인/생성/수정하는 기능은 v1에서 제외한다
- 채팅은 현재 화면 컨텍스트를 자동 주입하는 기능이 없으며, 사용자가 질문에 맥락을 직접 넣는 것을 전제로 한다
- MCP/조회 API는 외부 에이전트/LLM이 데이터를 읽을 수 있게 하는 레이어이며, 화면 단일 API와 책임을 분리한다

### 3.4 반응형 범위

- v1은 데스크톱 중심이고, 화면 폭은 사이드바와 채팅 패널을 제외한 중앙 영역이 최소 요구 폭을 만족해야 한다
- 모바일/좁은 화면 대응은 backlog

## 4. 공통 데이터/도메인 규칙

### 4.1 핵심 엔티티

- `tasks`: 확정된 작업 단위. `due_date`, `status`, `project_id`, `source_candidate_id` 등은 화면별로 확장 필요
- `meetings`: 회의 일정/녹음/요약 정보. Outlook 일정과 녹음이 매칭되는 구조
- `slack_daily_summaries`: 채널별 일간 요약 결과
- `extracted_candidates`: 아직 확정되지 않은 태스크 후보
- `dependencies`: 태스크 간 선후행 관계
- `human_review_log`: 승인/수정/반려와 같은 사용자 검토 이력

### 4.2 공통 시간 기준

- 미팅은 캘린더 시각 기준으로 본다
- Slack 요약은 새벽 5시를 하루 경계로 처리한다
  - 요약 날짜 D는 D 05:00 ~ (D+1) 05:00 사이의 대화를 포함
- Yesterday/Follow-up Task 화면은 이 경계를 그대로 사용한다

### 4.3 자료의 상태 표현

- `pending`: 아직 검토 필요
- `approved` / `rejected` / `edited`: 리뷰 상태
- `processing` / `done` / `failed`: STT/요약 파이프라인 상태
- `in_progress` / `done` 등은 태스크 상태와 일정 추적에 같이 활용

### 4.4 같은 데이터, 다른 소비층

- BFF(서비스 백엔드)는 화면용 API에 유리하게 필드를 빠르게 추가/변경할 수 있다
- MCP/조회 API는 외부 에이전트용으로 별도 API 계약을 유지한다
- 같은 DB를 읽더라도 화면과 외부 도구는 각각 독립적으로 진화해야 한다

## 5. 공통 운영 규칙

### 5.1 에러 처리

- 요약 생성 실패해도 원본 데이터는 열람 가능해야 한다
- STT 자체 실패 시 원문이 없으므로 원본 보기 대신 실패 상태를 안내한다
- Outlook 동기화 실패는 화면 전체를 막지 않고 경고 배너/마지막 동기화 시각으로 처리한다

### 5.2 검토 흐름

- 후보는 Inbox/Today/Yesterday의 Follow-up Task 탭에서 공통으로 검토된다
- 승인/반려/수정 후 승인은 같은 `extracted_candidates` 데이터와 리뷰 로그를 재사용한다
- 한 화면에서 처리된 데이터는 다른 화면에서도 즉시 반영된다
